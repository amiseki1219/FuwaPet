## 2. コンセプト・世界観

### アプリコンセプト

**「自分だけのキャラクターを、1年かけて育て、その後も日常のトモダチとして過ごす癒しAIアプリ」**

### 感情体験の系統

「たまごっち系 × どうぶつの森系 × シムズ系 × ヤンデレコレ系」の融合。
**ポケモン系（進化・バッジ図鑑）は除外**。

共通する設計思想: **「キャラが自立した存在として、そこに居る」**

### ターゲットユーザー

- 日常の癒やしを求めるユーザー
- 推し活・キャラ愛着の文化に馴染みがある層
- 20代〜40代女性をコア想定、性別問わず使える設計

### ビジュアルトーン

- パステルカラー × ネオン × 雲 × 星モチーフ
- ゆるふわな温かみと、少しの特別感
- **絶対に事務的な言葉を使わない**（例: 「ユーザー登録」→「住人登録」、「ログイン」→「お帰りなさい」）

## 3. キャラクター設計

### キャラクター5人

| キャラ | 動物 | 性格 |
|--------|------|------|
| ぽこ | トイプードル | 太陽みたいに明るい天真爛漫。ポジティブ全開でいつも元気いっぱい |
| える | 黒猫 | 冷静沈着でミステリアス。実は誰より優しい紳士的な存在 |
| ここ | うさぎ | 愛にあふれたおっとり癒し系。包み込むような愛情で安心感を与える |
| ぱる | 白猫 | 高飛車でツンデレ。心を開いた相手にだけデレを見せる |
| ぴよこ | ひよこ | おやつを見つけると一直線！元気いっぱいでちょっぴり破天荒なひよこ |

### キャラ取り扱い方針（D案採用）

- チュートリアルで5体の中から1キャラを選び、出会う
- **他4キャラは最初から存在を匂わせる**（お店や街での登場）
- 解放条件:
  - **メインキャラでLv.100カンスト → 2体目を無料で迎えられる**（約5年・指数曲線設計）
  - **その2体目もLv.100カンスト → さらに次の1体を無料解放**（以降も同様に1体ずつ）
  - **即解放（課金）: 廃止**（1キャラへの深い愛着を育てることがアプリの核）

### キャラクターニックネーム機能

ユーザーがキャラに独自の呼び名を付けられる（例: える → くろちゃん）。

**変更ルール（案B: 制限付き変更可能）**:
- Lv.1〜2: 自由に変更可能（慣れるまでの猶予期間）
- Lv.3以降: 変更時に確認ダイアログ表示
- Lv.4以降: 変更時にキャラが悲しむ演出 + 信頼度 -50pt
- 変更履歴は内部で記録（感情レポートの演出に活用）

## 4. 信頼度システム

### 設計コンセプト（2026/6/17 確定）

**最高レベルLv.100制（指数曲線設計）**

- 最初はガンガン上がり、レベルが上がるほど大変になる指数曲線設計
- 無課金フル活用: 153pt/日 × 約1,827日（**約5年**）でLv.100カンスト
- Lv.100到達者特典: **等身大ぬいぐるみ先着500体プレゼント**（コミュニティで希少価値を高める設計）
- 課金で信頼度上昇を加速可能（デイリーキャップなし）

### 累計必要pt テーブル

| Lv | 累計必要pt |
|---|---|
| 10 | 800pt |
| 20 | 3,000pt |
| 30 | 8,000pt |
| 40 | 20,000pt |
| 50 | 45,000pt |
| 60 | 90,000pt |
| 70 | 155,000pt |
| 80 | 220,000pt |
| 90 | 270,000pt |
| 100 | 296,000pt |

### 関係ステージ

| 段階 | 状態 | 目安pt | 口調 |
|------|------|--------|------|
| 初期 | 他人 | 0 pt | 距離感・敬語 |
| 序盤 | 知り合い | 100 pt 相当 | やや柔らかく、でも敬語 |
| 序盤 | 友達 | 500 pt 相当 | 敬語残しつつ本音が見える |
| 中盤 | 親友 | 1,500 pt 相当（口調変化ここで完成）| 深い感情表現 |
| 以降 | 特別なパートナー | — | 口調変化なし、思い出軸で醸成 |

※具体的なLvしきい値は実装時に調整

### ポイント変動

**加点のみ、減点は廃止**（癒しアプリの世界観を守る）。

| アクション | 増減 |
|-----------|------|
| 毎日ログイン | +10 pt |
| ごはん | +5 pt |
| なでなで | +3 pt |
| 会話（1送信） | +2 pt |
| 有償アイテムをプレゼント | +50 pt |

**代わりに以下を実装**:
- 久しぶりログイン時の「寂しかったよ」セリフ
- 連続ログインボーナス強化
- キャラが「話したいこと」を溜めておく（ログイン時に一気に話してくれる）

### Lv別解放体験（一部）

各Lvで解放される体験（詳細は実装時に確定）:
- 序盤Lv: キャラの過去の話解放
- 中盤Lv: 「約束」機能（v1.1以降）、キャラの夢・将来の話
- 高Lv: キャラの弱み・秘密の相談、キャラからの特別な呼び名
- **Lv.100: カンスト達成 + 等身大ぬいぐるみ先着500体プレゼント + 次のキャラ解放**

### ユーザー体験曲線

| 期間 | フェーズ | 体験の主軸 |
|------|---------|-----------|
| 1〜2週目 | 出会い期 | 口調が変わる驚き、キャラを知る |
| 1〜3ヶ月 | 関係構築期 | 信頼度を上げる楽しさ |
| 3〜6ヶ月 | 深化期 | 思い出の蓄積、性格変化が見えてくる |
| 6〜12ヶ月 | 結実期 | 関係性の完成、記念日イベント |
| 1〜5年 | 日常・深化期 | 生活の一部、Lv.100を目指す長期目標（**サブスク継続の鍵**） |
| 5年達成 | カンスト | Lv.100到達・特典受取・次キャラ解放 |

## 5. 状態パラメータシステム

### 内部パラメータ（DB保存）

| パラメータ | 範囲 | 減少 | 回復手段 |
|-----------|------|------|---------|
| おなか | 0-100（下限10） | 1h あたり -5 | ごはん+30、おやつ+10 |
| 元気 | 0-100（下限10） | 1h あたり -4 | ねんね+50 |
| 気分 | 0-100（下限10） | 自動計算（3パラ平均） | なでなで+3、会話+2 |
| 清潔 | 0-100（下限10） | 1h あたり -4 | お風呂+40 |

**下限10の設計理由**: 罪悪感を煽らない。0にはならず、キャラは「死なない」。

### キャラ別個性（パラメータ減少速度）

- **ぽこ**: おなか減少 +50%、気分減少 -20%（食いしん坊で明るい）

- **ここ**: 気分減少 +30%（寂しがり）

- **ぴよこ**: おなか減少 +40%、元気減少 +15%（食いしん坊で活発）

## 6. キャラ固有性格システム

**YURUFUワールドの核心機能**。同じキャラでも、ユーザーごとに育ち方で違う子になる。

### 2層構造

**層1: 不変コア（全ユーザー共通）**
- キャラの根本設定
- 基本口調、根底の性格、絶対守ること
- どう育ててもこれは変わらない

**層2: ユーザー固有性格（5パラ、行動で変化）**
- ユーザーの行動で徐々に変化
- 「うちのえる」を育てる要素

### 性格パラメータ5個

| パラメータ | 範囲 | 低値←→高値 |
|-----------|------|----------|
| 活動性 | -100 〜 +100 | おっとり ↔ 活発 |
| 甘えん坊度 | -100 〜 +100 | 自立 ↔ 甘えたい |
| 勤勉さ | -100 〜 +100 | マイペース ↔ 努力家 |
| 素直さ | -100 〜 +100 | ツンデレ ↔ ストレート |
| 感受性 | -100 〜 +100 | 冷静 ↔ 情緒豊か |

### キャラ別初期値

| キャラ | 活動性 | 甘えん坊 | 勤勉 | 素直 | 感受性 |
|--------|--------|---------|------|------|--------|
| ぽこ | +60 | +70 | 0 | +80 | +40 |
| える | -40 | -50 | +20 | -30 | -60 |
| ここ | -20 | +40 | -20 | +60 | +70 |
| ぱる | +30 | -60 | +10 | -80 | +20 |
| ぴよこ | +75 | +35 | -45 | +65 | +20 |

### AI学習要素

- **好きな話題**: 会話から推定、時系列で蓄積
- **嫌いな話題**: 同上
- **口癖**: ユーザーが繰り返す表現を学習

### 変化ロジック

**夜バッチで1日分の会話をまとめて分析**し、性格パラの変化量を決定。

例:
```
ユーザーが「お昼寝の話」をよくする
  → AIが「昼寝好きなのかな」と判定
  → える.好きな話題に「お昼寝」追加
  → える.活動性 -1
```

### 感情レポートでの見える化

成長の節目で「◯◯ちゃんの感情レポート」をユーザーに配信（詳細は別章）。

### 性格テキスト表示（Care画面・10種類）

#### 判定ロジック
5パラの組み合わせで以下の10種類から1つを表示する。
優先度順に上から判定する。

| 性格名 | 判定条件 |
|---|---|
| 太陽みたいな子 | 活動性≥50 かつ 感受性≥30 |
| クールな子 | 活動性≤-30 かつ 感受性≤-30 |
| 甘えんぼな子 | 甘えん坊度≥50 かつ 素直さ≥30 |
| ツンデレな子 | 甘えん坊度≤-30 かつ 素直さ≤-30 |
| 努力家な子 | 勤勉さ≥50 |
| マイペースな子 | 勤勉さ≤-30 かつ 活動性≤-20 |
| 情緒豊かな子 | 感受性≥50 かつ 甘えん坊度≥30 |
| 冷静沈着な子 | 感受性≤-30 かつ 活動性≤-20 |
| 活発で素直な子 | 活動性≥50 かつ 素直さ≥50 |
| おっとり癒し系 | 活動性≤-20 かつ 感受性≥50 |

※どの条件にも当てはまらない場合は「ふつうの子」を表示

- ぽこ（活動性+60・甘えん坊+70・素直+80・感受性+40）→「太陽みたいな子」
- える（活動性-40・甘えん坊-50・勤勉+20・素直-30・感受性-60）→「クールな子」
- ここ（活動性-20・甘えん坊+40・勤勉-20・素直+60・感受性+70）→「おっとり癒し系」
- ぱる（活動性+30・甘えん坊-60・勤勉+10・素直-80・感受性+20）→「ツンデレな子」

- 夜バッチで性格パラが変化
- Care画面を開くたびに最新の性格テキストを表示

## 9. AIシステム設計

> **【会話AI：OpenAIへの置き換え方針（2026/7/2 確定・モデル名は未確定）】**
>
> 会話AIを Gemini から OpenAI に置き換える方針とする。ただし、AI呼び出しの2段構成は維持する。
> - リアルタイム会話：低遅延・低コストの mini級モデルを使用する（候補例：GPT-5.4 mini など）
> - 夜バッチ分析：高品質なフル級モデルを使用する（候補例：GPT-5.5 / GPT-5.4 など）
> - 夜バッチは即時性が不要なため、Batch API の利用を検討する
> - 固定システムプロンプトが多いため、Prompt Caching の活用を検討する
> - 具体的なモデル名・単価は、タスク10着手時（2026/7/23予定）に OpenAI 公式の models / pricing を確認して確定する。候補例は括弧書き程度に留め、現時点ではモデル名を固定しない
>
> ※本メモ確定時点では、既存の Gemini 前提の記述（§9 使用モデル・コスト試算、§10 技術スタック、サブスク比較表のAIモデル行、CLAUDE.md のAI欄など）は据え置き。2026/7/23 のタスク10着手時に一括で整合させる。

### 呼び出し方式: 案C採用（リアルタイム + 夜バッチ）

- 朝の通知（JST 7:30）までに完了

```
【バックエンド + DB】 AWS
  ├─ API Gateway（エンドポイント）
  ├─ Lambda（ビジネスロジック、Gemini呼び出し）
  └─ DynamoDB（データ保存）

【AI】 Google
  └─ Gemini API（Flash / Pro）

【3D開発】 Meshy
  └─ image-to-3D, auto-rigging
```

この構成、Qiita記事ネタとしても超優秀。

### 一日の処理フロー例（Chat 1往復）

```
1. Unity → API Gateway にメッセージ送信
2. Lambda起動
3. DynamoDB GetItem: YurufuUsers[userId]
4. DynamoDB Query: YurufuEvents (SK begins_with "CONV#eru#", limit N)
5. DynamoDB GetItem: YurufuMemories[userId, "eru"]
6. 3,4,5を合体してプロンプト生成
7. Gemini Flash API呼び出し
8. 返答を取得
9. DynamoDB TransactWriteItems:
    - YurufuEvents にユーザー発言追加
    - YurufuEvents にキャラ発言追加
    - YurufuUsers の tickets -1、trustPoints +2、condition更新
10. Unity にレスポンス返す
```

DynamoDBアクセス4回/会話。1万人×10会話で月数千円規模。

## 16. キャラクター表現方針

### 採用方式: 3Dキャラクター（Meshy生成）

**Live2D は採用しない**。理由:
- キャラデザインが3Dレンダリング風で、Live2D化は困難（フェルト質感が崩壊する）
- Live2D学習コスト大（未経験で6ヶ月〜1年）
- **将来の部屋カスタム3D化との整合性**（Live2Dだと後で板キャラ問題発生）

### 技術スタック

- **Meshy**（$10/月 Pro プラン）: 画像→3D変換、自動リギング
- **Blender**（無料）: 3Dモデル微調整
- **BlenderMCP + Unity MCP**: Claude駆動で効率化

### 3D化パイプライン

```
Phase 1: キャラ3D化（1〜2週間）
  1. 既存キャラ画像を Meshy で image-to-3D
  2. 自動リギング（30秒）
  3. プリセット動作（idle, wave, jump等）適用
  4. FBX エクスポート

Phase 2: 品質調整（1〜2週間）
  1. Blender にインポート
  2. BlenderMCP で Claude と対話しながら調整
  3. マテリアル・質感・ポーズ微調整

Phase 3: Unity組み込み（1〜2週間）
  1. Unity に FBX インポート
  2. Unity MCP で Claude と対話しながら配置
  3. Animator で emotion 別アニメ切り替えスクリプト

合計: 4〜6週間（Live2Dの1/5〜1/10の工数）
```

### スプライトアニメ案はフォールバック扱い

Meshy 試験の結果によっては、スプライトアニメ + 表情差分にフォールバック可能。
判断タイミング: える1キャラで Meshy Pro 試験後。

### リスクと対策

| リスク | 対策 |
|--------|------|
| Meshy品質がキャラデザインに合わない | 1キャラ試験 → 不合格ならフォールバック |
| 3Dの学習コスト | BlenderMCP + Unity MCP でAI駆動開発 |
| スマホパフォーマンス | Low Poly モード、LOD設定、モバイル最適化 |
| Meshy依存 | 月$10のサブスク、中断可能 |

## 付録D: 実装詳細方針（黄項目の決定内容）

### D.1 エラーハンドリング方針

#### エラーレベル分類

| レベル | 内容 | 対応 |
|--------|------|------|
| Level 1 | 再試行で回復（ネット切れ、タイムアウト） | リトライボタン + キャラセリフ |
| Level 2 | ユーザー操作で解決（チケット不足、課金失敗） | 解決方法を提示 |
| Level 3 | サーバー側問題（AWS/Gemini障害） | メンテ画面、公式Twitter誘導 |
| Level 4 | 致命的エラー（データ不整合） | アプリ再起動を促す |

#### エラーシーン別の文言

**AI応答失敗（世界観を壊さないキャラセリフ）**:
```
ぽこ: "あれ、ちょっと頭がぼーっとしちゃった… もう一度話しかけてみて？"
える: "…少し考えがまとまらないようです。もう一度お願いできますか"
ここ: "あ、ごめんね〜… ちょっとお話できなくなっちゃった"
ぱる: "ちょっと！今調子悪いんだから、後にして！"
ぴよこ: ぴよよ…ちょっと迷子になっちゃった！もう一回話しかけてみてね
```

**ネット切れ（事務的な表示）**:
```
"電波が届かないみたい… Wi-Fi か通信状況を確認してね"
```

**課金失敗（信頼性を保つ事務的表示）**:
```
"購入できなかったみたい… もう一度試してみる？"
```

#### 設計原則

- AI失敗 = キャラセリフで（世界観維持）
- 通信/課金失敗 = 事務的表示（誤解招かない）
- サーバー障害 = メンテ画面（状況を明確に）

- 条件: 最終ログインから3日経過
- 文言: "えるが寂しがってるよ…"（キャラ別文言あり）

**報酬系**:

- 条件: 新しい感情レポートが生成された時
- 文言: "えるからあなたへのメッセージが届きました 💌"
- 頻度: プランによる（月1〜毎日）

レベルアップ通知:
- 条件: Lv.2, 3, 4等の到達時
- 文言: "えると知り合いになりました！"（Lv.2の場合）
- 頻度: イベント時

**リマインド系**:

ごはん通知:
- 条件: おなか < 20 が4時間続いた時
- 文言: "えるのおなかがすいてるみたい…"
- 頻度: 1日最大1回

- 条件: 7日目到達前日
- 文言: "明日は連続ログイン7日目！大きなボーナスがもらえるよ"
- 頻度: 予告日のみ

- 1日に複数通知は送らない（迷惑防止）
- 全て設定画面でON/OFF可能
- 深夜（22時〜朝7時）は送らない
- キャラの世界観に合った文言
- 無視された通知を同内容で連続送信しない

- イベント通知: Lambda内から即時送信

## 付録E: プラン変更時の挙動

### 変更反映タイミング

| 変更種別 | 反映タイミング |
|---------|--------------|
| アップグレード | 即時反映（上位プラン特典を即解放）|
| ダウングレード | 次回更新日に反映（現プランは期限まで維持）|
| 解約 | 次回更新日に無料プラン化 |

**ダウングレード・解約は日割り返金なし**（利用規約に明記）。

### 記憶容量が減る時の挙動

**例**: 仲良し（50件）→ 寄り添い（20件）

- DB: 変化なし（全保存方針）
- AIプロンプト: 参照件数が50→20に減少
- UI: Chat履歴スクロールは全件閲覧可能
- 体験: 「キャラが最近のことしか覚えてない…」切ない、でも許容範囲

### 性格パラメータの扱い

**例**: 運命の絆 → 仲良し

運命の絆限定機能（口癖の無制限記憶、ユーザー口癖の真似、2人の思い出の言葉）:
- DB: データは残す
- 機能: 次回更新日から停止
- 再加入: データ復活、機能も復活
- **「記憶は残ってるけど、キャラが特別な関わり方を忘れる」演出**

### 有償コイン♡・アイテム・連続日数

- **有償コイン♡**: 既存分は保持、毎月付与のみ停止
- **アイテム・衣装**: 既に所持したものは解約後も保持
- **連続サブスク日数**: 累計加入日数でカウント（一度解約してもリセットされない）

### 解約防止UI

**実装しない**。理由:
- ダークパターン認定リスク（ストア審査で弾かれる可能性）
- 癒し系アプリの世界観と矛盾
- 誠実さを優先

解約ボタン押下 → そのまま解約確認 → 解約完了。シンプルな動線。

## 付録H: 通信エラー・サーバー障害時の対応

### ローカルキャッシュ戦略

**キャッシュするもの**:
- 最新のユーザーデータ（YurufuUsers主要項目）
- 最近の会話履歴（直近20件）
- キャラ固有性格（YurufuMemories）
- 所持アイテム情報

**キャッシュ更新タイミング**:
- アプリ起動時
- 会話後
- お世話後
- サーバーからのレスポンス成功時

### サーバー復旧後の同期

- **v1.0ではオフライン時の書き込み操作を禁止**しているため、同期が必要なローカル変更は発生しない
- 復旧検知: アプリがネット復旧を検知したら自動で最新データ取得
- ユーザー通知: なし（裏でサイレント処理）

### サーバー障害時のUX

**AWS側の障害**:
```
メンテナンス画面:
  「ただいま、ゆるふわ〜るどに
   メンテナンスがあります
   しばらくお待ちください
   
   最新情報: @yurufu_official」
```
公式Twitter（要開設）に復旧情報を投稿。

**Gemini障害**:
- Chat画面のみ使えなくなる
- Care画面等は通常通り使える
- ユーザーへの案内: 「AIが少し不調みたい…」

**Firebase障害**:
- 認証が使えない
- 既にログイン済み: キャッシュで動作継続
- 新規ログイン: 不可

### エラーログ収集

**Firebase Crashlytics 導入**:
- アプリクラッシュの自動記録
- スタックトレース取得
- ユーザー操作の痕跡
- リリース後の障害即把握
- **転職武器**（「Crashlyticsで障害監視」は評価される）

   - ⚠️ 微妙 → Blender で修正可能性を検討
   - ❌ 不合格 → 代替手段を検討

### I.2 夜バッチ時刻（JST基準）

**決定**: 日本時間 **3:00 AM**（UTC 前日 18:00）に統一。

**理由**:

- 深夜3:00は日本人のログイン率が最も低い
- 朝7:30の通知配信までに分析完了している必要がある

**将来の多言語展開時**:
v2.0以降でタイムゾーン別バッチに移行。例:
- 日本: JST 3:00
- 米西海岸: PST 3:00
- 欧州: CET 3:00

### I.3 HOME画面の役割明確化

**決定**: HOME画面は起動時の「Tap to Start」専用画面。

**画面遷移**:

```
【アプリ起動】
  HOME画面（Tap to Start）
    ↓ タップ

    ↓
```

### I.4 Issue粒度の考え方

**原則**: **1 Issue = 1〜3日で完了できる単位**

**理由**:
- 完了感を得やすい（モチベ維持）
- PR レビューがしやすい
- 途中でブロックされても他 Issue に移れる

**Level 1 Issue の分割試案**（参考、実際の分割は Level 0 完了時に相談）:

```
【バックエンド基盤】
  AWSアカウント詳細設定（IAM、リージョン、予算アラート）
  AWS CDK (TypeScript) プロジェクト雛形作成 ← ※1
  API Gateway + Lambda のHello World API
  DynamoDB: YurufuUsers テーブル作成
  DynamoDB: YurufuEvents テーブル作成
  DynamoDB: YurufuMemories テーブル作成
  Repository パターン実装（DB抽象化層）

【認証基盤】
  Firebase プロジェクト詳細設定
  Unity に Firebase SDK 導入
  匿名認証実装（Unity側）
  Firebase Auth Admin SDK を Lambda に導入
  Lambda でトークン検証実装
  新規ユーザー作成API連携

【通信基盤】
  Unity → API Gateway の通信ラッパー作成
  エラーハンドリング基本形
  ローカルキャッシュ層の基礎実装

【統合テスト】
  「起動 → 匿名認証 → ユーザー作成 → データ取得」のE2E確認
```

### ※1 IaC ツール選定（宿題メモ）

**推奨: AWS CDK (TypeScript)**

**CDK 推奨の理由**:
- SAM は YAML 中心で表現力が弱く、分岐やループを書くのが辛い
- CDK なら TypeScript でコード化、L2 コンストラクトが充実
- 転職アピールとして CDK の方が評価高い（IaC の現代的標準）
- Claude Code との相性も CDK の方が良い（TypeScript 生成精度が高い）
- Qiita 記事化しやすい

**学習コスト懸念**:
- TypeScript 未経験だと学習コストあり
- ただし CDK で書く TypeScript は限定的（複雑な機能不要）
- C# 経験者は比較的スムーズに入れる
- Claude Code の補完があれば書ける

**代替案: SAM**
- TypeScript 学習コストを避けたい場合
- Level 0 進捗が予定より遅れてスピード優先したい場合
- YAML に慣れてるなら選択肢としてあり

**決定タイミング**: Level 1 着手直前（Level 0 完了時）
- Level 0 完了時点で僕（チャット）に相談
- TypeScript への抵抗感、進捗状況、CDK 公式チュートリアルの感触で判断
- 最悪 SAM で始めて後で CDK 移行も可能

**合計 16〜17 Issue**、2ヶ月で消化なら週2 Issue ペース。

**実装時の注意**:
- AWS は想定より詰まりやすい（認証、権限、リージョンエラー等）
- Firebase と AWS の連携部分は特に時間がかかる可能性
- 進捗に応じて粒度を調整（途中で1 Issue を2つに分割等）

## ウィジェット機能（iOS限定・v1.1以降）

### コンセプト
ホーム画面にキャラクターを表示し、ログイン状況に応じて表情が変化する。
Duolingoウィジェットのようなエンゲージメント促進機能。

| サイズ | 内容 |
|--------|------|
| Small | キャラ画像 + 表情のみ |
| Medium① | キャラ画像 + 一言セリフ |
| Medium② | キャラ画像 + ステータスバー3つ |
| Large① | キャラ画像 + 一言 + ステータスバー |
| Large② | キャラ画像 + 信頼度Lv + 一言 |

### ログイン状況による表情変化
| 状態 | 表情 | セリフ |
|------|------|--------|
| 当日ログイン済み | 通常 | 「今日もよろしくね！」 |
| 1日未ログイン | しょんぼり | 「会いたいよ…」 |
| 2日未ログイン | 悲しい | 「どこにいるの…？」 |
| 3日以上未ログイン | 元気ない | 「寂しいよ…」 |

### 技術仕様
- プラットフォーム: iOS限定（v1.1）、Android対応はv1.2以降検討
- 実装: WidgetKit（Swift）
- データ共有: App GroupsでUnityのセーブデータと共有
- キャラ画像: WidgetKit用静止画を表情別に用意
- 対応キャラ: ユーザーが選択中のキャラクターを表示
